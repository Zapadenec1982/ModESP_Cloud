# ModESP Cloud — Можливості платформи

**Мультитенантна IoT-платформа для моніторингу комерційного холодильного обладнання, відповідності HACCP та дистанційного керування пристроями.**

> Побудовано на Node.js, PostgreSQL, MQTT, Svelte — розгорнуто на Linux VPS із TLS на всіх рівнях.

---

## Загальний огляд

| Показник | Значення |
|----------|----------|
| API-ендпоінти | 90+ REST |
| Канали реального часу | MQTT + WebSocket |
| Параметри пристрою | 48 на пристрій (температури, аварії, налаштування) |
| Типи аварій | 10 (критичні / попередження / інформаційні) |
| Тестове покриття | 130+ інтеграційних тестів |
| Мови інтерфейсу | Українська, Англійська, Польська, Німецька |
| Розгортання | Продакшн на Hetzner VPS, TLS/HTTPS |

## 1. Мультитенантність

Повна ізоляція орендарів на кожному рівні — база даних, MQTT-брокер, API та інтерфейс.

- **CRUD орендарів** — створення, перейменування, деактивація орендарів з тарифними планами (free / basic / pro / enterprise)
- **Ізоляція даних** — кожен SQL-запит обмежений `tenant_id`; MQTT-топіки фізично розділені за slug орендаря
- **Крос-тенантні операції** — суперадмін бачить усіх орендарів, переміщує пристрої між ними
- **RBAC з урахуванням орендаря** — користувачі належать до одного або кількох орендарів; адмін бачить лише дані свого орендаря
- **Перемикання орендарів** — мультитенантні користувачі обирають активного орендаря при вході або перемикаються під час сесії
- **Партнерський план** (епік 2.5) — сервісна компанія на плані «Партнер» створює організації своїх клієнтів (`tenants.parent_tenant_id`), ставить у них своїх техніків із роллю на кожну організацію, бачить аварії, наряди, рекомендації і точки всіх клієнтів на одній сторінці «Клієнти» і входить у будь-яку з них одним кліком. Клієнти партнера поділяють його платіжний рахунок (`billing_accounts`) — основа для зведеного рахунку епіка 2.2. Партнер А не бачить клієнтів партнера Б; адмін клієнта не бачить інших клієнтів партнера
- **Брендування** (функція плану `branding`) — назва, логотип і сайт організації на публічних сторінках статусу точок і в HACCP-звітах; клієнт без власного бренду показує бренд партнера

## 2. Управління пристроями

Повний життєвий цикл від виробництва до експлуатації — автовиявлення, призначення, моніторинг, перепризначення.

### Автовиявлення та провізіонінг
- ESP32-пристрої самореєструються через MQTT із спільним bootstrap-ключем
- Нові пристрої з'являються в черзі **Очікуючих пристроїв** зі статусом онлайн/офлайн
- Адмін призначає пристрій орендарю → платформа автоматично генерує унікальні MQTT-облікові дані та доставляє їх по повітрю (OTA)
- Провізіонінг без втручання: пристрій перепідключається з новими обліковими даними автоматично

### Властивості пристрою
- Назва, розташування, серійний номер, модель, дата виробництва, коментарі
- Прив'язка до торгової точки — країна, область, місто й адреса живуть на точці і спільні для всіх пристроїв за цією адресою
- Географічні координати (широта/довгота) як необов'язковий override над координатами точки
- Версія прошивки та версія протоколу відстежуються через heartbeat
- Статус онлайн/офлайн у реальному часі (поріг heartbeat — 90 секунд)

### Стан у реальному часі
- 48 параметрів оновлюються в реальному часі: температури (повітря, випарника, конденсатора), уставка, стан компресора, цикл розморожування, стан дверей, захисні аварії, налаштування термостата
- Стан відображається в UI з групуванням за категоріями (Обладнання, Термостат, Розморожування, Захист)
- WebSocket push — інтерфейс оновлюється миттєво без опитування

### Перепризначення пристрою
- Суперадмін переміщує пристрій між орендарями в один клік
- Автоматична ротація облікових даних, очищення RBAC та міграція MQTT-топіків
- 120-секундний grace-період запобігає хибним сповіщенням про офлайн під час переходу

## 3. Дистанційне керування

Надсилання команд на пристрої з хмари — через REST API або веб-інтерфейс.

- **Редагування параметрів** — зміна уставки термостата, інтервалів розморожування, порогів захисту дистанційно
- **Валідовані команди** — приймаються лише параметри, дозволені для запису (визначені в схемі метаданих пристрою)
- **Повне оновлення стану** — запит на повторну публікацію всіх 48 параметрів на вимогу
- **MQTT-доставка** — команди публікуються в MQTT-топіки конкретного пристрою з гарантіями QoS
- **Рольовий доступ** — лише ролі admin та technician можуть надсилати команди; viewers — тільки перегляд

## 4. Телеметрія та аналітика

Серверне семплювання з гнучкими запитами та агрегацією часових рядів.

### Збір даних
- 6 каналів телеметрії з семплюванням кожні 5 хвилин: температура повітря, температура випарника, температура конденсатора, уставка, компресор (вкл/викл), розморожування (вкл/викл)
- 30-секундний дебаунсинг запобігає дублюванню записів при швидких змінах стану
- Щомісячні партиції PostgreSQL — автоматичне створення та очищення через 90 днів

### API запитів
- **Сирі дані** — до 10 000 точок за запит із заголовком `X-Truncated` при обрізанні
- **Агреговані статистики** — min / max / avg за часовий бакет (5хв, 15хв, 1год, 6год, 1день)
- **Фільтрація каналів** — запит лише потрібних каналів
- **Гнучкий часовий діапазон** — ISO-мітки часу або відносні години (за замовчуванням 24 год, максимум 31 день)

### Інтерактивні графіки
- Багатоканальний лінійний графік (uPlot) із зумом, паном, легендою
- Накладення подій — цикли компресора, старти розморожування, аварії відображаються як пунктирні вертикальні лінії
- Розгортуваний журнал подій під графіком

## 5. Відповідність HACCP та експорт даних

Вбудовані інструменти для відповідності вимогам харчової безпеки (регуляції HACCP України).

### Експорт CSV
- **CSV телеметрії** — журнали температур із мітками часу, UTF-8 BOM для сумісності з Excel
- **CSV інвентаризації пристроїв** — усі пристрої з властивостями (назва, модель, розташування, серійний номер, прошивка)
- **CSV історії аварій** — з фільтрацією за серйозністю та діапазоном дат (до 90 днів)

### PDF-звіт
- **Температурний звіт HACCP** — професійний PDF із зведеною статистикою, хронологією аварій, погодинним журналом температур
- Підтримка кирилиці (шрифт Roboto) — готовий для подання в українські регуляторні органи
- Генерація на сервері (pdfmake) — без залежності від браузера

### Обмеження запитів
- 10 експортів на хвилину на користувача — запобігає зловживанню без блокування легітимного використання

## 6. Система аварій

10 типів аварій із класифікацією за серйозністю, затримками для уникнення хибних спрацювань та багатоканальними сповіщеннями.

### Типи аварій та серйозність

| Серйозність | Аварії |
|-------------|--------|
| **Критична** | Висока температура, Низька температура, Відмова датчика 1, Відмова датчика 2 |
| **Попередження** | Відкриті двері, Безперервна робота, Збій охолодження |
| **Інформаційна** | Аварія швидкості зміни, Короткий цикл, Швидкий цикл |

### Розумне виявлення
- Моніторинг переходів булевих станів (off→on = аварія піднята, on→off = знята)
- **Затримки проти хибних спрацювань** — аварія дверей чекає 2 хвилини, аварія охолодження — 5 хвилин перед підтвердженням
- Мітки часу активації/зняття з відстеженням тривалості

### API аварій та UI
- Фільтрація за серйозністю, активні/зняті, пристрій, діапазон дат
- Статистика аварій — кількість та середня тривалість за кодом аварії
- Фільтри серйозності в UI (Усі / Критичні / Попередження / Інформаційні) для швидкого аналізу
- RBAC на рівні пристрою — користувачі бачать аварії лише для призначених пристроїв

## 7. Енергомоніторинг

Розрахункове енергоспоживання на основі профілів потужності моделей обладнання.

### Оцінка енергоспоживання
- Час роботи компресора x номінальна потужність → розрахункові кВт·год за інтервал семплювання
- Розбивка за компонентами: компресор, нагрівач відтайки, вентилятори, споживання в режимі очікування
- Профілі моделей обладнання (таблиця device_models) з індивідуальними перевизначеннями потужності на пристрій
- Розрахунок вартості з налаштовуваним тарифом на електроенергію для кожної організації

### Сумісність з майбутніми датчиками
- Зарезервований MQTT-ключ `equipment.energy_kwh` для реальних CT clamp датчиків енергії (майбутня прошивка)
- Автовиявлення: якщо прошивка публікує `equipment.energy_kwh`, семплер використовує реальне значення замість розрахункового
- Прапорець `energy_source`: `estimated` (за замовчуванням) або `metered` (CT clamp)

### UI та API
- Вкладка Енергія на сторінці деталей пристрою — графік кВт·год, зведення вартості, розбивка за компонентами
- Канал енергії (`energy`) на графіку телеметрії поряд з каналами температур
- `GET /api/devices/:id/energy/summary` — підсумки кВт·год, вартість, розбивка за компонентами

## 8. Торгові точки та географія

Фізичні об'єкти як повноцінна сутність — одна адреса, багато пристроїв — плюс усе, що сервісна
організація насправді робить з картою.

### Торгові точки
- Точка — це один фізичний об'єкт (магазин, склад, цех) з країною, областю, містом, вулицею й індексом
- Пристрій належить максимум одній точці; точка тримає скільки завгодно пристроїв — магазин з десятьма шафами це одна позначка на карті, а не десять
- `location` зберігає старий сенс: вільний текст про місце **всередині** точки («Зал, ряд 3»), а не адреса
- Власні координати пристрою лишаються необов'язковим override над координатами точки — на карті спершу береться координата пристрою, потім точки
- Наявні значення `location` переносяться в точки під час міграції, тож після оновлення карта вже заповнена
- Назви точок унікальні в межах тенанта; порівняння нечутливе до регістру й пробілів

### Геокодування на боці сервера
- Адреса → координати через бекенд-проксі (Nominatim). Браузер ніколи не звертається до геокодера напряму: один ідентифікований User-Agent, один темп 1 запит/с, один спільний кеш — рівно те, чого вимагає політика використання OSM
- Структуровані запити (вулиця / місто / країна) для точок; вільний текст — тільки для рядка автодоповнення, де користувач вводить довільне
- **Перевірка країни** — результат, чия країна суперечить запитаній, вважається відсутністю збігу. Зіпсований запит падає тихо й упевнено: поламана кирилиця повертає французькі департаменти з високими оцінками релевантності й без жодної помилки. Саме ця перевірка стоїть між демо-картою і флотом, який «раптом опинився у Франції»
- Постійний кеш із двома термінами життя: збіги 180 днів, справжня відсутність збігу 6 годин, транспортні збої не кешуються взагалі — одна невдача провайдера не має робити адресу негеокодовною на пів року
- Автодоповнення адреси й перетягуваний маркер зі зворотним геокодуванням в інтерфейсі
- Повністю опційно: з `GEOCODER_PROVIDER=none` автодоповнення ховається, а платформа працює далі на введених вручну координатах

### Карта флоту
- Кластеризовані маркери, по одному на точку, з кольором за найгіршим статусом пристрою в кластері
- Панель фільтрів: країна, область, місто, точка, модель, версія прошивки, статус пристрою, призначений користувач, вільний пошук, видима область карти
- Шар теплокарти аварій, агрегований у SQL за будь-який період
- Ізохрони доїзду (15 / 30 / 60 хв) — справжні полігони часу доїзду з ключем OpenRouteService; без ключа — кільця прямої відстані, які інтерфейс **видимо позначає як наближені**, щоб жодне рішення про виїзд не спиралося на коло, прийняте за полігон
- Клік-для-розміщення координат, живі оновлення статусів через WebSocket і список «без координат» — усе збережено з початкової карти

### Гео-аналітика
- Деталізація вглиб: країна → область → місто → точка
- По кожній групі: кількість пристроїв / онлайн / офлайн / в аварії, аварії за період, середня температура повітря, uptime %, оцінені кВт·год, сервісні виїзди
- Сортовна таблиця і CSV-експорт з тими самими фільтрами і тими самими правилами доступу — метрика, яку не можна порахувати дешево, повертається як null, а не вигаданим нулем

### Планувальник сервісного обʼїзду
- Мультивибір точок на карті → оптимізований порядок обʼїзду (задача комівояжера в OSRM), лінія маршруту, відстань і час по кожній ділянці
- Передача маршруту на телефон посиланням Google Maps із проміжними точками
- Без сервера маршрутизації планувальник усе одно відповідає: порядок «найближчий сусід» і deep-link не потребують зовнішнього сервісу взагалі, а результат підписаний «орієнтовно, без оптимізації за часом у дорозі»
- Найближчі до точки техніки, впорядковані за відстанню від домашньої бази, з реальним часом у дорозі, коли маршрутизація налаштована. Адмін бачить id, email, адресу бази, відстань до 0.1 км і час; технік — знеособлений підпис, без адреси і з відстанню, округленою до цілих кілометрів: 0.1 км по трьох точках дала б координату бази колеги. Запит по точці вимагає того самого доступу, що й читання самої точки. Ніколи токени, telegram id чи хеші паролів

### Зовнішня погода
- Поточні умови й погодинний прогноз по кожній точці (Open-Meteo), історія зберігається 395 днів, щоб порівняння рік-до-року продовжувало працювати
- **Зовнішня температура як друга серія на графіку телеметрії пристрою**, на власній правій осі — це головна віддача функції: саме вона пояснює стрибки навантаження і просідання COP, які на власних кривих шафи виглядають безпричинними
- Таймзона точки (IANA) заповнюється автоматично з тієї ж відповіді — без додаткових залежностей і ручного вводу
- Поллер робить один запит на кожну унікальну округлену координату, а не на кожну точку

### Доступ на рівні точки
- Видати техніку цілу точку замість того, щоб відмічати пристрої по одному; пристрої, додані на цю точку пізніше, покриваються автоматично
- Ефективний доступ — обʼєднання гранта на пристрій і гранта на точку; наявна модель per-device не змінилася
- Гранти несуть власний тенант, тож грант, отриманий в одному тенанті, нічого не дає під час роботи в іншому
- Технік редагує власну домашню базу з меню користувача в бічній панелі (`PATCH /api/profile`); адмін може задати її будь-кому зі сторінки «Користувачі»

### Публічні посилання на статус
- Поділитися з клієнтом read-only сторінкою статусу однієї точки — без логіну, без облікового запису, без застосунку
- Токен — 32 випадкові байти, зберігається лише як sha256-хеш, показується рівно один раз при створенні і передається заголовком запиту, тож не потрапляє ні в access-лог, ні в `Referer`
- Термін дії обовʼязковий (90 днів за замовчуванням), посилання відкликається, кожне має лічильник переглядів
- Сторінка показує лише назву точки, місто / область / країну і по кожному пристрою — підпис, ознаку онлайн, температуру повітря й ознаку аварії. Жодних id, серійних номерів, версій прошивки, slug тенанта чи координат точніших за місто
- Відкликаний, прострочений і неіснуючий токени не відрізнити: всі три дають однакову 404, тож сторінка ніколи не підтверджує, що токен існував

### Треті сторони — демо-конфігурація
Геокодування, погода, маршрутизація та ізохрони — усі ENV-керовані, викликаються лише з сервера і при
вимкненні деградують у робочий вимкнений стан, а не в помилку. Поточне розгортання використовує їхні
безкоштовні / некомерційні тарифи **для демонстрації**. ModESP Cloud — комерційний продукт, тож перед
продакшном кожен із них потребує платного плану або self-hosted інстансу; чекліст — у
`docs/THIRD_PARTY_LICENSING.md`. Атрибуція `© OpenStreetMap contributors` показана на кожній карті і
не може бути прибрана.

## 11. OTA-оновлення прошивки

Завантаження, розгортання та моніторинг оновлень прошивки — один пристрій або масове розгортання на флот.

### Бібліотека прошивок
- Завантаження `.bin` файлів (до 4 МБ) з тегом версії, типом плати, примітками до релізу
- SHA-256 контрольна сума обчислюється при завантаженні, перевіряється пристроєм при скачуванні
- Перевірка сумісності плати — запобігає розгортанню неправильної прошивки на неправильне обладнання

### Розгортання на один пристрій
- Розгортання в один клік з UI або API
- MQTT-команда з URL завантаження, версією, контрольною сумою
- Відстеження статусу: в черзі → відправлено → успіх / невдача (тайм-аут 10 хвилин)
- Версія до OTA зберігається для надійного виявлення успіху через heartbeat

### Групове розгортання
- Обрати прошивку + список пристроїв → розгортання в налаштовуваних пакетах
- **Розмір пакету** — скільки пристроїв на хвилю
- **Інтервал пакетів** — секунди між хвилями (запобігає перевантаженню мережі)
- **Поріг невдач** — автоматична пауза розгортання, якщо відсоток невдач перевищує налаштоване значення
- Адмін може відновити призупинене розгортання
- Витримує перезапуск сервера — відновлюється з бази даних при старті

### Фоновий моніторинг
- Опитування кожні 30 секунд: порівняння версії прошивки пристрою з очікуваною після OTA
- Автоматичне виявлення успіху/невдачі без зворотного виклику від пристрою

## 12. Управління користувачами та автентифікація

Автентифікація на основі JWT із 4-рівневим RBAC та контролем доступу на рівні пристрою.

### Автентифікація
- **JWT-токени** — access-токен на 15 хвилин, refresh-токен на 30 днів із ротацією
- **Політика паролів** — мінімум 15 символів (відповідно до NIST SP 800-63B, без вимог до складності)
- **Перевірка HaveIBeenPwned** — клієнтська k-anonymity перевірка проти бази скомпрометованих паролів
- **Обмеження запитів** — 50 спроб входу / 5 хвилин / IP
- **Зміна пароля** — вимагає верифікацію старого пароля, видає нові токени

### Рольовий контроль доступу (RBAC)

| Роль | Область | Можливості |
|------|---------|------------|
| **Суперадмін** | Уся платформа | Усі операції, крос-тенантний доступ, аудит-лог, CRUD орендарів |
| **Адмін** | Свій орендар | Повний контроль: пристрої, користувачі, прошивки, сповіщення |
| **Технік** | Призначені пристрої | Перегляд, надсилання команд, розгортання прошивки, сервісні записи |
| **Спостерігач** | Призначені пристрої | Доступ лише для читання (без команд, без редагування) |

### Призначення пристроїв
- Адмін призначає конкретні пристрої технікам/спостерігачам
- Контроль на рівні API — несанкціонований доступ до пристрою повертає 403
- Масове призначення/відкликання через API
- Аудит-слід призначень (ким надано, коли надано)

### Призначення торгових точок
- Адмін видає цілу точку замість того, щоб відмічати пристрої по одному; пристрої, додані на точку пізніше, покриваються автоматично
- Ефективний доступ — об'єднання гранта на пристрій і гранта на точку; модель per-device не змінилася
- Гранти несуть власний тенант, тож грант, отриманий в одному орендарі, нічого не дає під час роботи в іншому
- Редагується в тому ж модальному вікні, що й призначення пристроїв: Скасувати відкидає обидві зміни, Зберегти застосовує обидві

### Мультитенантне членство
- Користувачі можуть належати до кількох орендарів (зв'язок M:N)
- **Роль на кожне членство** (`user_tenants.role`, епік 2.5) — одна людина може бути адміном у своїй компанії і техніком у клієнта; access-токен несе роль саме тієї організації, в яку увійшли, і змінюється при перемиканні. Запрошення дає роль, на яку запрошували, навіть наявному акаунту
- Вибір орендаря при вході, якщо є кілька членств
- Перемикання орендаря під час сесії без повторного входу

### Прив'язка Telegram
- Згенерувати код прив'язки у веб-інтерфейсі → надіслати Telegram-боту → обліковий запис з'єднаний
- Команди бота враховують RBAC-роль та призначення пристроїв користувача

## 13. Аудит-логування

Незмінний, append-only журнал аудиту для відповідності та безпеки.

- **Автоматичне захоплення** — усі операції створення/оновлення/видалення логуються без змін коду в маршрутах
- **Записані поля** — користувач, дія, тип/ID сутності, зміни до/після (JSON diff), IP-адреса, user agent, мітка часу
- **Незмінність** — тригер PostgreSQL забороняє UPDATE/DELETE в таблиці аудит-логу
- **API запитів** — фільтрація за орендарем, типом сутності, дією, користувачем, діапазоном дат (тільки суперадмін)
- **Веб-інтерфейс** — сортована таблиця з фільтрами, переглядач JSON diff для змін до/після
- **Fire-and-forget** — записи аудиту ніколи не блокують основний запит

## 14. Комунікація в реальному часі

Два канали реального часу — MQTT для пристрій-хмара, WebSocket для хмара-браузер.

### MQTT (Пристрій ↔ Хмара)
- Ієрархія топіків: `modesp/v1/{орендар}/{пристрій}/state/{ключ}` (48 індивідуальних скалярних топіків)
- Heartbeat кожні 30 секунд із версією прошивки, аптаймом, вільним heap, RSSI WiFi
- TLS-шифрування на порту 8883 із сертифікатом Let's Encrypt
- Брокер Mosquitto з PostgreSQL-backed ACL (плагін go-auth)

### WebSocket (Хмара → Браузер)
- JWT-автентифіковане з'єднання (`ws://host/ws?token=...`)
- Обмеження за орендарем — клієнти отримують оновлення лише для пристроїв свого орендаря
- Типи повідомлень: дельта стану (лише змінені ключі), аварія, статус пристрою
- RBAC на рівні пристрою — підписка перевіряється відповідно до призначень пристроїв користувача
- Обробка протитиску — пропуск повідомлень, якщо буфер клієнта перевищує 64 КБ

## 16. Інфраструктура та експлуатація

Готове до продакшну розгортання з TLS, резервними копіями та моніторингом.

### Безпека
- HTTPS скрізь (Let's Encrypt, автоматичне поновлення)
- MQTT TLS на порту 8883
- ESP32 перевіряє серверний сертифікат через вбудований набір CA
- Хешування паролів bcrypt (фактор вартості 12)
- CORS обмежений продакшн-доменом
- Незмінний аудит-лог

### База даних
- PostgreSQL 16 з пулом з'єднань (макс. 30 з'єднань)
- Тайм-аут запитів (30с) запобігає зависанню запитів
- Щомісячні партиції телеметрії з автоматичним створенням та очищенням через 90 днів
- 18+ таблиць з індексами, зовнішніми ключами та обмеженнями

### Моніторинг
- `GET /api/health` — статус бази даних, MQTT, аптайм
- Моніторинг StateMap — кількість пристроїв, загальна кількість ключів, оцінка використання пам'яті (логується кожні 60с)
- Структуроване логування Pino (JSON у продакшні)

### Резервне копіювання та обслуговування
- Щоденний дамп PostgreSQL о 2:00 (зберігання 30 днів)
- Очищення партицій телеметрії о 3:00 щодня
- Попереднє створення місячних партицій (25-го числа кожного місяця)

### Розгортання
- systemd-сервіс з автоматичним перезапуском
- Nginx reverse proxy з підтримкою WebSocket upgrade
- Розгортання через Git (`git pull` + `systemctl restart`)

## 18. Рекомендації з обслуговування

Аварію визначає контролер: він сам рахує пуски компресора, час роботи, таймаути відтайки і
піднімає `rapid_cycle_alarm`, `continuous_run_alarm`, `high_temp_alarm` тощо. Хмара порогів не
дублює. Те, чого контролер не бачить, — це історія: одна й та сама аварія на одній камері
третій раз за тиждень — це вже не привід для ще одного підтвердження, а привід для візиту.
Саме це й робить єдине правило (`maintenance_rules`, платформне значення + перевизначення
організації, за бажанням — окремо на модель обладнання):

| Ознака | Що читається | Що порадить |
|---|---|---|
| Аварія повторюється | той самий код аварії від контролера на пристрої ≥ N разів за вікно (за замовчуванням 3 за 7 днів); `device_offline` не рахується | «Контролер піднімає цю аварію знову і знову — потрібен візит: призначте наряд» |

- **Одна підказка на пристрій і код аварії** — відкривається, коли лічильник сягає межі, оновлюється,
  поки вікно ще тримає стільки аварій, закривається сама (`resolved`), щойно старі аварії випадають з вікна.
- **Життєвий цикл** — «взяти в роботу» (технік із доступом до пристрою), «відхилити» (адмін; наступної
  години підказка повернеться, якщо аварії нікуди не ділись), «призначити наряд» — діалог з вибором
  виконавця прямо з підказки; історія на вкладці пристрою й у списку організації.
- **Сповіщення** адміністраторам як `info` (Telegram, пошта, web push) з назвою аварії, кількістю та вікном;
  WebSocket `hint` оновлює плитку на панелі та бейдж на картці пристрою наживо.
- **Пороги** (N і вікно в днях) редагує адмін організації в Налаштуваннях; платформні — superadmin.
  Функція плану `maintenance` — з тарифу «Обʼєкт».
- **Ретенція** закритих підказок — `MAINTENANCE_HINT_RETENTION_DAYS` (365).

Лічильники самого контролера (`defrost.consecutive_timeouts`, `protection.compressor_starts_1h`,
`protection.compressor_duty`, мотогодини) видно на графіку й у стані пристрою — без порогів на сервері.

Що далі (не в цьому епіку): вебхук-подія `hint.opened` (епік 2.6), калібрування N і вікна на реальних
даних пілотів.

## 19. Наряди на роботу

Аварія або рекомендація стає нарядом; наряд має виконавця, точку з адресою, пріоритет і розклад;
закриття наряду пише структурований сервісний запис (хто, скільки часу, які запчастини, скільки
коштувало). Саме цей ланцюжок — аварія → наряд → візит → запис — дозволяє рахувати попереджені
ремонти, а не кількість сповіщень.

- **Звідки береться** — кнопка «Наряд» біля аварії, «Створити наряд» у рекомендації, з картки пристрою
  або вручну на сторінці «Наряди». Створення з аварії підтверджує її, з рекомендації — рекомендацію.
- **Хто що може** — адмін призначає будь-кого й скасовує; технік бере наряд собі, але не передає колезі;
  старт і закриття — виконавець або адмін; глядач лише бачить наряди на своїх пристроях.
- **Виконавцю** приходить сповіщення з назвою точки, адресою і посиланням на маршрут у Google Maps
  (Telegram, пошта, web push); WebSocket оновлює списки наживо.
- **Закриття** — виконані роботи, тривалість, запчастини (назва; кількість; вартість), вартість і валюта
  → `service_records` з `user_id` і `work_order_id`; старий список сервісних записів пристрою бачить його.
- **Статистика** — кількість по статусах, скільки з аварій і з рекомендацій, середній час до призначення,
  старту і закриття за період.

Що далі: збережені обʼїзди з планувальника, фото до сервісного запису, метрики нарядів у гео-статистиці.

## 20. Білінг

Рахунок формується з даних системи, а не з таблиці в Excel: щогодини платформа фіксує, скільки контролерів,
точок і користувачів має кожна організація (`usage_snapshots`), а 1-го числа виставляє рахунок за попередній
місяць зі середньоденного використання × ціни плану. Оплата — банківським переказом; карткові платежі
з'являться разом із договором еквайрингу.

- **Що в рахунку** — абонплата плану (пропорційно дням існування організації в місяці), контролери за
  об'ємною ціною (від 100 — 80 грн, від 500 — 60 грн на «Мережі»), точки для плану «Мережа». Контролер, що
  працював тиждень, коштує чверть місяця. Планам без цін (Enterprise) і нульовим сумам (Старт) рахунок не
  виставляється.
- **Партнер** отримує один зведений рахунок: абонплата «Партнера» плюс рядок «контролери» на кожного клієнта
  за партнерським тарифом; клієнт бачить лише «рахунки виставляються партнеру».
- **PDF і лист** — рахунок мовою організації (uk/en/pl/de) з реквізитами постачальника, призначенням платежу
  й вкладенням у листі на `billing_email` (або адміністраторам).
- **Дунінг** — через 7 днів після строку організація стає «прострочено» (банер у застосунку, лист), через
  14 — повторне нагадування, через 21 — «призупинена» (вхід і дані з контролерів блокуються, контролери
  працюють автономно). Оплата або анулювання рахунку повертає доступ автоматично.
- **Сторінка «Оплата»** для адміна: план і ціни, оцінка поточного місяця, як оплатити, платіжні дані
  організації, рахунки з PDF, використання за місяцями, заявка на зміну плану.
- **«Білінг»** для superadmin: усі рахунки з фільтром і діями «оплачено / анулювати / надіслати», завдання
  вручну (знімок, рахунки за період, дунінг), заявки на зміну плану, реквізити постачальника.

- **Запобіжники** — рахунки не виписуються, поки не заповнені назва постачальника та IBAN (без них рахунок
  неможливо оплатити), а рахунок, який не було надіслано, зупиняється на статусі «прострочено» і ніколи не
  призупиняє організацію. Тобто автоматика не може тихо відключити парк через рахунок, якого клієнт не бачив.

Що далі: карткові платежі (WayForPay / LiqPay) з фіскалізацією Checkbox, акт для B2B, імпорт банківської виписки.
